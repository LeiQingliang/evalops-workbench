# 从反馈到固定评测集

## 1. 先定义问题与检查方法

每条反馈先归为账号、账单、功能、隐私等场景。固定 `id`，整理原问题和经人工确认的参考答案。把可以确定检查的内容写为必含词、禁用词；语气、事实依据和复杂推理保留人工判断。避免用“正确”“准确”等宽泛标签包装简单规则。

## 2. 保留两个可复核版本

在同一批问题上保存改动前后回答，并记录提示词版本、模型配置、采样参数和采集日期。当前工具不自动采集这些元信息，可在实验说明中记录。不要用不同问题数量或不同用户群的回答直接做版本比较。

## 3. 看逐条变化

规则通过率 = 所有启用规则均通过的样本数 / 固定问题总数。每个样本默认也检查回答非空。

- `regression`：基线通过、候选失败，优先检查。
- `improvement`：基线失败、候选通过，仍需要确认改善是否真实。
- `unchanged_pass`：两版都通过。
- `unchanged_fail`：两版都失败。

同一回答可触发多个失败原因，失败原因计数不能相加当作失败样本总数。平均耗时、费用和人工分数只在有值的记录中计算，覆盖数必须一起呈现。输入缺失不等于零成本或零耗时。

## 4. 形成运营复盘

建议为每次实验保存：目的、样本范围、版本配置、失败案例、人工复核意见、待修改项、复测结果。将高频反馈补充进评测集，并保留少量历史问题，防止改动解决新问题却破坏旧流程。

内置演示故意让总通过率上升、同时保留一条退步，用来练习这种检查方式。所有回答和数值都是合成数据。

## 与 Langfuse 的字段映射建议（未在线实现）

| 本项目字段 | 可以考虑的 Langfuse 对象 |
| --- | --- |
| `id` / `question` | dataset item 标识与 input |
| `reference_answer` | expected output |
| 两版 `response` | 各自实验的输出 |
| 文本规则结果 | 独立命名的规则 score |
| 人工评分 | 人工标注 score，记录评分标准与评分人 |
| 耗时、费用 | 来自真实 trace 的测量信息；不要用演示值替代 |

官方参考：[Datasets & Experiments](https://langfuse.com/docs/evaluation/experiments/datasets)。此表是设计建议，不是已完成的 SDK 接入、上传功能或兼容性保证。需要联网集成时，先确认当前 API、权限和数据处理约定。

## 已知局限

1. 子串匹配不理解否定、同义词、事实真假和语境；包含关键词不保证回答正确。
2. 参考答案只展示给人看，工具没有用它计算语义相似度。
3. 人工分数来自输入，工具不能保证标注一致性；应另做抽样复核。
4. 测量值来自输入；工具不计时、不估算 token、不核验费用。
5. 不做显著性检验。少量固定案例适合回归检查，不能推断真实用户总体效果。
6. 每个版本每个问题只能有一条回答；随机模型需要多次采样的场景，当前应拆分明确的样本 ID 并另行设计统计方法。
